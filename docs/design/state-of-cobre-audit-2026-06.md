# State of Cobre — Comprehensive Codebase Audit

**Date:** 2026-06-13 · **Baseline:** `main` @ `6333bffd` (v0.8.1 released today)
**Scope:** Read-only audit across **performance, architecture, code quality, documentation**
**Method:** 30 deep-read audit cells → per-finding adversarial verification → per-dimension synthesis → completeness critic (120 agents, ~8.4M tokens). Findings below are post-verification; refuted claims removed.

## 1. Executive summary

**Cobre is a mature, disciplined codebase.** After adversarially verifying every medium-and-above
finding against the actual code, **zero critical and zero high-severity issues survived** — the
27 confirmed mediums and 120 lows are improvement opportunities, not defects. There are **no
correctness, determinism, or Python-parity bugs** in the audited surface. The hard rules
(`unsafe_code = forbid`, `unwrap_used = deny`, no `Box<dyn Trait>`, infrastructure-crate genericity,
bit-for-bit determinism, no hot-path allocation) are not just aspirational — they are visibly and
consistently honored in the code.

The single most important pattern across **all four dimensions** is the same: **load-bearing
invariants and facts live in places the compiler does not check** — prose comments, `debug_assert!`
(compiled out in release), doctests, design-doc status banners, hand-mirrored version pins, and
duplicated error/parity tables. Nothing is wrong _today_; the risk is silent drift on the _next_
edit. The consistent remedy is to make the compiler or a small CI guard the single source of truth.

A second, more localized pattern: the recent **module reorganization** and **DCS remediation** —
both landed and shipped in v0.8.1 — left a trail of stale pointers in agent-/maintainer-facing docs
(`architecture-rules.md`, `docs/design/*.md` status banners, `file.rs:NNN` anchors). These are the
bulk of the documentation findings. They are trivial to fix but actively misleading.

## 4. Performance

Performance discipline in this codebase is genuinely strong: the hottest training loops (forward/backward solve, lower-bound evaluation) already use pre-allocated scratch buffers, in-place stats primitives, and bit-deterministic warm-starting, and many candidate "hot-path allocation" findings turned out to be either already-reused buffers or one-time setup costs. The verifiers downgraded a large fraction of the high-severity submissions — the most common pattern was conflating a worst-case tail bound (the ~60k cut pool) with the steady-state operating point, or proposing optimizations that collide with the bit-determinism hard rule. The two clearest _net-new_ wins are unconditionally-run out-of-sample sampling slow paths whose fast paths were built and then never wired in (`SobolPrecomputed`, point-wise LHS), and the simulation I/O writer that funnels a fully parallel compute pass through one drain thread. No correctness defects were found; every item is either a throughput opportunity or documentation drift.

### Top issues

**SIM-PERF-01 — Single-threaded Parquet writer serializes a parallel compute pass (High).** Simulation compute runs across all rayon workers (`state.rs:338-343` `workspaces.par_iter_mut()`), but every `SimulationScenarioResult` is pushed through one bounded `mpsc::sync_channel` (default capacity 64, `config/simulation.rs:32`) into a single `std::thread::spawn` drain loop (`crates/cobre-cli/src/commands/run/simulation.rs:56,69`). That thread calls `write_scenario`, which has 10 independent entity blocks (`crates/cobre-io/src/output/simulation_writer.rs:526-717`), each doing `create_dir_all(scenario_id={id:04}/)` + temp-file create + ZSTD-3 Parquet encode + rename (`atomic.rs:133-168`, codec at `parquet_config.rs:59`). Because it is a `sync_channel`, once the writer saturates, compute workers block in `dispatch_scenario_result` (`pipeline.rs:1012-1020`). The verifier corrected the severity claim to Medium-with-caveat: partitions are keyed solely on `scenario_id` (`simulation_writer.rs:529`), so round-robin sharded writers need no ordering constraint — but the "wall time governed by the writer, not LP solves" claim is unmeasured. Next step: profile the writer thread (split ZSTD-encode cost from dir-create/rename syscall cost) at production scenario counts, then shard the drain across threads or batch many scenarios per file.

**STO-PERF-01 / STO-PERF-02 — Out-of-sample sampling runs slow paths whose fast paths were built and abandoned (High / High, both confirmed at Medium).** The only production entry into OutOfSample noise generation hardcodes `sobol_ctx = None` (`crates/cobre-stochastic/src/sampling/class_sampler.rs:275`), so every scenario point calls `scrambled_sobol_point`, which rebuilds the Joe-Kuo direction matrix and re-derives scramble params per draw (`tree/qmc_sobol/mod.rs:302-303`) — identical for every scenario at a given `(seed, iteration, stage_id, dim)`. The `SobolPrecomputed` struct and `scrambled_sobol_point_precomputed` were written to amortize exactly this and have no non-test caller. The LHS analogue is worse: `sample_lhs_point` reruns a full Fisher-Yates shuffle of `total_scenarios` per dimension and keeps only `perm[scenario_idx]` (`tree/lhs.rs:157-164`), giving O(S²·dim) where O(S·dim) suffices. Both verifiers confirmed the mechanics and downgraded to Medium only because the blast radius is the non-default OutOfSample/QMC convergence-validation case, not every run. These are the cleanest wins: the Sobol fix reuses an already-tested fast path; the LHS fix hoists permutations into a per-stage context. Note STO-PERF-02's recommendation cites `SobolPrecomputed` as a live analog — it is not yet plumbed, so both fixes need a precomputed-context parameter threaded through `fill()`/`sample()`.

**PERF-LP-01 / FWD-03 — Full LP re-upload per (stage, scenario) on the forward path (High → Medium).** On the baked path the inner per-scenario loop calls `reset_solver_state()` then `load_model(&params.baked[t])` (`crates/cobre-sddp/src/training/forward_pass_state.rs:730,738`), a complete CSC re-upload via `cobre_highs_pass_lp` (`crates/cobre-solver/src/backends/highs/interface.rs:182-199`) whose `num_nz` grows with the active cut count. The reload is the determinism mechanism for HiGHS (`reset_solver_state` is the trait-default no-op for HiGHS — `trait_def.rs:293` — only CLP overrides it). The verifier corrected three things: the cost is _already instrumented_ (`total_load_model_time_seconds` / `load_model_count`, `interface.rs:223-224`), so the "single largest LP-build cost" claim is unmeasured; a HiGHS bounds-only re-patch (recommendation (a)) would leak prior-scenario bounds and simplex state and **violates the bit-determinism hard rule** — withdraw it; and the only contract-safe lever is routing high-cut-count stages through the existing DCS lazy path (`ctx.templates[t]` + `lazy_solve_preloaded`, `stage_solve.rs:74-76`), which excludes inactive cut rows. Measure load-model share first; any persistent-model reuse must stay within one iteration's inner scenario loop (templates re-bake between iterations as the pool grows) and remain HiGHS-only.

**BWD-01 — Static equal-count trial-point partition cannot absorb load imbalance (High → Medium).** The backward region spawns one rayon task per worker (`backward_pass_state.rs:926-930`), each running a sequential loop over an equal-_count_ slice (`for m in start_m..end_m`, `:987`; `partition()` is ceiling-division by count, `solve/partition.rs:20-30`). Per-trial-point cost is highly data-dependent (`reset_solver_state` fires per trial point at `:1004`, warm chains only span openings _within_ a trial point), so equal counts ≠ equal work, and once slices are handed out rayon has nothing finer to steal. The imbalance is measured (`stage_imbalance_ms = max_worker - avg_worker`, `:545`, summed into `BackwardResult::load_imbalance_ms`, `mod.rs:191-197`) but never acted on. The verifier flagged two corrections: `max - avg` is a coarse diagnostic, _not_ "a third of backward wall time" — the "~33%" is a separate unvalidated lead, and any claimed speedup must be re-measured net of the per-stage serialized `cut_sync` (`:843-851`) and metadata sync (`:853`). The recommendation also under-scopes the work: parallelizing over trial points requires re-architecting not just the `agg_arena` indexing but the per-worker `basis_slices` sub-views (`BasisStore::split_workers_mut`, `workspace.rs:1021-1042`), which hand each worker a disjoint `&mut` slice keyed to its scenario range. Prototype behind the existing diagnostic and validate the realized gain before treating it as a third of backward time.

**PERF-HOT-01 / PERF-DCS-RESCORE — DCS re-gathers and re-GEMMs the candidate set every inner round (Medium, confirmed).** `score_violated_candidates` clears `cand_coef_block` and re-walks `pool.active_cuts()`, copying each non-resident in-window candidate's full `n_state` row (`crates/cobre-sddp/src/cut/dcs.rs:331-349`) then running one `gemm_block` (`:358-367`), up to `max_inner_iterations` (default 50, `:81`) times per opening. Residency shrinks the set by only `nadic` (default 10) per round, so early rounds rescan nearly the whole non-resident pool; with the default `k1 = None` (`:76`) the recency window applies no filter. This is the concrete mechanism behind the known multi-cut/60k-pool scoring risk, but it is gated behind `cut_selection.method = Dynamic` (off by default), so it cannot regress the shipping backend, and the cost is instrumented (`scratch.scoring_time_seconds`, `:782`). The verifier's correction matters: the GEMM is **not** reusable — `alpha = grad · x*_raw` and `x*_raw` (the outgoing state) changes every resolve, so the dirty-set idea from PERF-DCS-RESCORE's recommendation does not apply. Only the _gather_ is invariant. The defensible fix is to gather once and, on later rounds, drop the rows whose slots became resident (in-place compaction, O(`nadic·n_state`)) rather than re-gathering; the full GEMM per round is intrinsic to re-scoring at a new optimum. The existing `k1` recency window is the already-built lever for capping the gather and is simply disabled by default.

**FWD-01 — Per-stage `statistics()` clones a Vec three times per LP solve (High → Medium).** Inside `run_forward_worker`, every (scenario, stage) calls `ws.solver.statistics()` twice (`crates/cobre-sddp/src/training/forward_pass_state.rs:815,825`); `statistics()` is `self.stats.clone()` (`highs/interface.rs:519-521`), allocating a fresh `retry_level_histogram: Vec<u64>` (`types.rs:201`), and `SolverStatsDelta::from_snapshots` `.collect()`s a third Vec (`solver_stats.rs:95-100`) — three heap allocations per LP solve, purely for diagnostic per-stage attribution. This is a direct violation of the "never allocate on hot paths" rule, and the fix already ships in-repo: the backward pass does it correctly via `statistics_into(&mut buf)` against per-worker scratch (`trial_point.rs:219-222,261-262`). The verifier downgraded to Medium (the histogram is ~12 `u64`, allocations are tiny and short-lived) and corrected the recommendation: reuse the existing `accumulate_into` against two `statistics_into`-filled scratch buffers held on the workspace rather than inventing a new in-place `from_snapshots`. Low effort, clear hard-rule fix.

### Cross-cutting patterns (performance)

- **"Fast path built, never wired in."** Three independent findings (STO-PERF-01 `SobolPrecomputed`, STO-PERF-02 LHS precompute, CLP-HOTSTART-DEAD) describe a complete, tested optimization that sits as dead code while a slower path runs in production. The sampling two are genuine forfeited wins; the CLP one is a deliberate capability seam over an existing native warm path. Worth a sweep to either wire or delete.
- **Determinism-mandated reloads are the recurring "false bottleneck."** PERF-LP-01/FWD-03, BWD-03, and SIM-PERF-05 all flag a per-unit full model reload that is actually the bit-determinism mechanism (HiGHS `reset_solver_state` is a no-op, so the `pass_lp`/`load_model` _is_ the reset). Multiple recommendations proposed skipping it; all such proposals collide with the cross-rank bit-determinism hard rule and were withdrawn or narrowed to the contract-safe DCS lazy path. The legitimate lever is bounding the _active cut count_ (cut selection), not skipping the reload.
- **Worst-case pool size cited as the operating point.** BWD-02, PERF-LP-02, PERF-ACTIVECUTS-SCAN, and the DCS findings all invoke the ~60k cut pool; verifiers repeatedly noted that 60k is a tail bound (capacity = `warm_start + max_iterations × forward_passes`, `pool.rs:849`), and production caps the active set via cut selection — so several "linear-in-pool" costs are bounded in practice.
- **Cost is already instrumented in most hot-path findings.** `load_model_time_ms`, `bwd_solve_time_ms`, `load_imbalance_ms`, `scoring_time_seconds`, and `bake_time_ms` already exist. The right disposition for most Medium/Low items is _profile against the existing counter first_ — the codebase's "measure first" rule applies, and few of these findings carry a profile.
- **Documentation drift on perf-relevant claims.** MPI-05, BWD-04 (dangling `docs/design/*.md` references deleted in `fb54670a`), BWD-05 (stale `backward.rs:NNN` pins after the split), and TRAITDEF-COMMIT-HASH-DATE-LEAK (commit hash + dates in shipped rustdoc) are trivial prose fixes that mislead cost/behavior reasoning.

## 5. Architecture

The crate layering is fundamentally sound: the dependency graph is a strict acyclic DAG with three independent leaf foundations (core, solver, comm), the genericity hard rule is essentially satisfied at the lexical level, and the most-cited cohesion risk — DCS dual-path proliferation — has been genuinely retired for the backward pass via an enum-dispatched `StageOpeningSolver` seam (verified). Adversarial verification deflated most of the originally-flagged structural concerns: the two "god-files" are 80-86% inline tests, the genericity "violations" are vocabulary smells rather than rule breaches, and the config-layering concern is speculative future-proofing with no second vertical to block today. What remains genuine and actionable clusters in two places: **release/manifest mechanics** (hand-maintained version pins, MSRV drift, ambiguous publish intent for stub crates) and **error-taxonomy consistency** (the same `SddpError` value classified differently by CLI vs Python). No finding carries a correctness, determinism, or parity bug — every survivor is maintainability, ergonomics, or release-hygiene debt.

### Top issues expanded

**ARCH-REL-005 — Release mechanics carry 22 hand-pinned version literals plus an MSRV drift (medium, confirmed).** Every intra-workspace dependency carries both `path` and a literal `version = "0.8.1"` because Cargo rejects `version.workspace = true` inside a dependency spec (empirically confirmed against cargo 1.94.1). **GEN-03 — `StageTemplate` carries SDDP/PAR semantics in an infra-crate doc comment (medium, confirmed).** Five scalar fields on the "backend-agnostic" `StageTemplate` (`crates/cobre-solver/src/types.rs:283-311`) describe SDDP-vertical structure in their doc text — "AR lags" (`:290`), "hydros"/"PAR lag order"/"FPHA" (`:297`), "Number of operating hydros" (`:303`), "Maximum PAR order" (`:306,:308-309`), and `dual[0..n_dual_relevant]` gradient extraction (`:300`) — directly contradicting the struct's own claim that the solver "treats it as an opaque data holder and does not interpret the LP structure" (`:243-244`). ### Cross-cutting patterns (architecture)

Two themes recur across the survivors. First, **prose-as-contract rot**: the recurring defect is a comment, doctest, or design doc asserting a present-tense relationship that the compiler does not enforce and that has silently gone false — `factory.rs:17` (STUB-02), the `checkpoint_interval` doctest (CFG-03), the "opaque data holder" claim on `StageTemplate` (GEN-03), and the architecture-debt doc that still says "deferred — no changes now" for shipped work (DCS-ARCH-02). Each is a doc-integrity failure mode and warrants a mechanical backstop (a compiled doctest that means it, or a guard test) rather than a one-time fix. Second, **hand-mirrored duplication with no sync guard**: parallel per-crate version pins (ARCH-REL-005, ARCH-DEP-001/002), four hand-copied lint blocks that have already drifted (cobre-python missing `too_many_arguments = "deny"`), two independent error-mapping tables (ERR-03), and the forward/sim/backward lazy-solve sequence (DCS-ARCH-01) all share the shape "the source of truth exists but is only half-applied." The consistent remedy is to make the compiler or a small CI check the single authority — exhaustive destructures, `{ workspace = true }`, a single `category()` mapping — so a partial edit fails loudly instead of drifting.

### Cross-cutting patterns (documentation)

- **Reorg/remediation drift dominates.** The module reorganization and the DCS remediation are the root cause of the majority of confirmed findings: deleted files/symbols dangling in `architecture-rules.md`, `:NNN` anchors into removed files, a "not yet wired" header on now-live code, and two completed design docs still labeled "deferred." ## 8. What this review did NOT cover (follow-up pass)

The audit was dense on the SDDP hot path (cut/DCS/backward/forward) and on doc/architecture drift, but several subsystems and analysis modalities were untouched. These are the highest-value gaps to close next:

### Subsystems with little or no coverage

- **Convergence / stopping rules** (`crates/cobre-sddp/src/convergence/`, ~1250 LOC) — _entirely absent_ from the 147 findings, yet this decides _when training ends_. Worth auditing: `evaluate_bound_stalling`'s relative-improvement denominator near LB≈0 and under the CVaR LB>UB regime; `RuleSet::evaluate` multi-rule combination determinism; `evaluate_simulation_based` rank-count invariance under MPI.
- **`horizon_mode` / Cyclic (steady-state) horizon** — not analyzed at all. A whole execution mode (back-edges, terminal-value handling, discount factors) with its own correctness contracts; the entire inventory implicitly assumed the finite/acyclic path.
- **Atomic output / durability** (`cobre-io/src/output/atomic.rs`) — the module doc itself flags drop-flush error-swallowing and truncated-file-on-rename. Unverified: same-directory rename, parent-dir fsync after rename, and coherence of partial multi-file output sets on mid-write failure. This is the substrate under _every_ output file.
- **Policy export / load / provenance** (`cobre-sddp/src/policy/`, `output/policy/codec.rs`) — the FlatBuffers policy codec got one cast pass but no round-trip / back-compat / forward-compat audit despite being the persisted on-disk format; `provenance.rs` was never opened to confirm what it actually writes/validates.
- **Config validation** (`cobre-io/src/validation/schema.rs`, ~1432 LOC) — the user-input gatekeeper. Unverified whether it rejects the malformed inputs that elsewhere reach the solver as `unreachable!`/panic.

### Analysis modalities never run

- **Zero actual profiling numbers.** Every "hot path"/"load imbalance"/"GEMM cost" finding is _static reading_. The ~33% backward imbalance and 60k-pool cost are inherited leads, not re-measured. **Run `cpu-profiling` on the canonical `cobre_set_24_sc2` / convertido cases** and attach real percentages so the ~40 perf findings triage by impact, not inspection.
- **No supply-chain audit output.** `deny.toml` exists, but no `cargo deny check` / `cargo audit` _results_ were captured — open RUSTSEC advisories, duplicate transitive versions, license/yank status. Given the per-crate duplicated heavy deps, the transitive graph is unexamined.
- **No real multi-rank execution.** The single most important correctness contract (bit-for-bit determinism across MPI rank counts) is referenced in ~6 findings but never _exercised_ — every "4-rank" test is a single-process mock and the one `mpirun` test is `#[ignore]`'d. **Run the actual `mpirun` parity case** (MPICH is installed locally) on the local benchmark and `cmp` outputs across 1/2/4 ranks. Until then, the determinism findings are hypotheses.
- **CI/release robustness** of the 9 workflows was reasoned about, not re-exercised (wheel license injection, `check-doc-paths.sh`, the `cargo doc -Dwarnings` private-intra-doc trap).

### Under-covered surfaces

- **`cobre-python` parity is asserted, never differentially proven.** Parity is real but _split across modules_ (CLI writes `scaling_report`/`provenance`/`hydro_model_summary` from `commands/run/setup.rs:569-619`; Python from `run.rs:867-882`) — a new output added to one site can silently miss the other with no test catching it. **Enumerate every `cobre_io::write_*` call site in both crates and diff them.**
- **`cobre-cli` internals** — 116 `unwrap/expect/panic/unreachable` in non-test CLI code went uncounted (CLI is a binary, so `unwrap_used = deny` may not apply), but a panic in `report.rs`/`validate.rs`/`summary.rs`/`broadcast.rs` is still a user-facing crash with a bad message.
- **`cobre-io` Parquet schemas** were read only at the doc layer (column-count drift); the ~20 `output/*.rs` schema definitions were not audited for null handling, dictionary-encoding correctness, or Arrow↔Parquet logical-type fidelity.
- **Checkpoint/resume determinism** — `checkpoint_interval` is flagged as dead config, but whether a `--resume`d run is bit-identical to an uninterrupted one is untested (the determinism contract should span the checkpoint boundary).

## Appendix · Methodology

- **30 audit cells** across 4 dimensions (9 performance · 8 architecture · 7 quality · 6 documentation), each a deep-read agent scoped to specific paths with the project hard-rules and known leads as context.
- **Per-finding adversarial verification:** every medium-and-above finding was handed to a separate skeptic agent instructed to _refute_ it against the actual code, defaulting to refuted on weak evidence, and to correct over-/under-stated severity. **16 findings were refuted; many "high" claims were downgraded** — those corrections are reflected inline (the "High→Med" notation and the withdrawn determinism-violating recommendations).
- **Per-dimension synthesis** + a **completeness critic** (§8). Totals: 120 agents, ~8.4M tokens, 30/30 cells, 147 confirmed findings.
- **Quantitative metrics (§2)** were gathered directly (greps over the tree), independent of the agents.
- **Caveat:** all findings are static analysis. No code was profiled, no multi-rank run was executed, and no supply-chain scan was captured — the determinism and perf-ranking conclusions are therefore hypotheses to be confirmed by the follow-up pass in §8.
